# Configuration

Generated by `hearth config --markdown`; do not edit by hand. Every value hearth uses lives here, in `crates/hearth-core/config/hearth.toml`; put the keys you want to change in your own file (`$HEARTH_CONFIG`, or `~/.config/hearth/hearth.toml`). `hearth config` shows what is in effect and where each value came from.

## `[accelerators]`

| Key | Default | Meaning |
|---|---|---|
| `accelerators.query_timeout_ms` | `5000` | How long a GPU driver tool (nvidia-smi) may take to answer before it is killed and the query reported as failed. A wedged driver can leave it stuck in the kernel; doctor, fit and the metrics must not wait with it. |

## `[control]`

| Key | Default | Meaning |
|---|---|---|
| `control.max_clients` | `8` | Clients answered at once. Answers come from memory and take microseconds, so this only matters when clients stall; one beyond it is told hearthd is busy rather than queued. |
| `control.max_message_bytes` | `65536` | hearthd's control socket (hearth status, hearth restart, MCP). Requests and answers are a few hundred bytes of JSON; anything past this many bytes is refused, so a client cannot make hearthd hold arbitrary amounts of memory. |
| `control.timeout_ms` | `2000` | How long one exchange on the socket may take, from connecting to the last byte of the answer. A client that stalls holds its handler this long. |

## `[discovery]`

| Key | Default | Meaning |
|---|---|---|
| `discovery.first_contact_timeout_ms` | `2500` | How long to wait for an HTTP answer from a listening port that hearth has never probed before. A server that accepts the connection and never answers (a wedged scheduler, for example) is reported as unresponsive after this. Once a runtime has answered often enough, a deadline learned from its recorded answers replaces this value (see learned_deadline_multiplier). |
| `discovery.learned_deadline_floor_ms` | `50` | Shortest learned deadline. Runtimes on loopback often answer in well under a millisecond, and ten times that is less than the scheduling jitter of a busy machine probing many ports at once; below this floor a healthy runtime would be reported slow. |
| `discovery.learned_deadline_multiplier` | `10.0` | Once a runtime has answered on a port several times, its probe deadline is learned from those answers instead of first_contact_timeout_ms: the slowest answer recorded for that program on that port, times this multiplier, never more than first_contact_timeout_ms. A runtime that misses its learned deadline is asked again with the first-contact deadline before it is called unresponsive, and is reported as slow if it then answers. |
| `discovery.learned_from_snapshots` | `100` | How many of the latest ports snapshots deadlines are learned from. Every ports run reads them, hearthd's watch rounds included, so this bounds that work however long the history grows. |
| `discovery.learned_min_samples` | `3` | Recorded answers needed before the learned deadline replaces the first-contact one. |
| `discovery.max_probe_response_bytes` | `8388608` | Most bytes read from one probe response. Probes ask runtimes for small JSON documents; anything larger is not a runtime answering a probe. |

## `[gateway]`

| Key | Default | Meaning |
|---|---|---|
| `gateway.allowed_origins` | `[]` | Web pages allowed to call the gateway from a browser, by origin ("http://localhost:3000", an app's "app://name", or "null"). A request carrying any other Origin is refused, and so is a Host that is not an IP address or localhost, so a website cannot spend this machine's models (cross-site requests, DNS rebinding). Programs that are not browsers send no Origin and are not affected. |
| `gateway.body_timeout_ms` | `120000` | How long a client may take, in all, to send a body the gateway reads whole (one kept for retry, or an Ollama request to translate). Large base64 images over a slow link need more than the head's time. |
| `gateway.connect_timeout_ms` | `2000` | How long connecting to the server may take before the client is told it could not be reached. |
| `gateway.head_timeout_ms` | `10000` | How long a client may take to send its request line and headers. |
| `gateway.idle_timeout_ms` | `600000` | How long a request may go without a byte from the server before both sides are closed. Long enough for a large prompt's prefill, which sends nothing until the first token. |
| `gateway.listen` | unset | Where hearthd forwards requests to the servers it keeps: a request for /s/NAME/REST goes to server NAME as /REST, so a client's base URL is http://LISTEN/s/NAME/v1. A server that is not ready, or not configured, gets a JSON error saying what to do instead of a hang. Unset means off. Keep it on loopback: it forwards to the servers with no authentication. |
| `gateway.max_clients` | `64` | Requests forwarded at once; one beyond this is told the gateway is busy. |
| `gateway.max_head_bytes` | `65536` | Most bytes of one request's line and headers. Bodies are not limited: they stream through to the server as they arrive. |
| `gateway.per_server_concurrency` | `0` | Requests one server runs at once through the gateway; set it to the server's slots (llama-server -np). When it is full, requests wait their turn, round robin across apps (the X-Hearth-App header names one), so one app's batch cannot hold up another app's request. Waiting counts toward ready_wait_ms. 0 turns queuing off: everything goes straight on. |
| `gateway.ready_poll_ms` | `200` | How often a held request checks whether its server is ready, and a request waiting for its server's first byte whether its client is still there: a client that leaves cancels it then. |
| `gateway.ready_wait_ms` | `120000` | How long a request for a server that is starting, or waiting out a restart hearthd decided, is held before it is refused. A client that arrives during a restart is then served when the server is ready, not turned away. A stopped or given-up server is refused at once. |
| `gateway.retries` | `2` | How many times a request is sent again when its server fails before answering: the connection refused or closed, or a 5xx after which hearthd restarts it (a poisoned backend). Only while nothing has reached the client, and within ready_wait_ms in all. 0 turns retrying off. |
| `gateway.retry_body_bytes` | `2097152` | Largest request body kept so it can be sent again. Larger bodies, and chunked ones, stream through once and are never retried. At most max_clients bodies are held at once, so the worst case is this times max_clients (128 MiB at the defaults); raise it for large base64 images. |
| `gateway.retry_grace_ms` | `3000` | After a 5xx, how long to watch for hearthd restarting the server before passing the 5xx on as the application's own answer. |
| `gateway.translate_body_bytes` | `33554432` | Largest Ollama-API request (/api/chat, /api/generate) translated for a server that only speaks OpenAI's API. The body is read whole to translate it, so this bounds what one request holds; images in base64 count. Parsed and re-encoded, a body takes a few times its size, and max_clients requests can translate at once: lower this on a machine short of memory. |

## `[pressure]`

| Key | Default | Meaning |
|---|---|---|
| `pressure.psi_full_critical` | `20.0` | Critical when all tasks stalled together at least this percent of the time. For comparison, systemd-oomd's default is to start killing at 60. |
| `pressure.psi_some_warn` | `10.0` | Linux publishes no memory pressure level, only how much of the last ten seconds tasks stalled waiting for memory (PSI, /proc/pressure/memory). ## `[servers]`

| Key | Default | Meaning |
|---|---|---|
| `servers` | unset | Servers hearthd starts and keeps alive, one table each, named [servers.NAME] in your own file: port (where it listens), command (the program and its arguments, as a list), and optionally host (the address to probe, loopback when unset) and expect (part of the model name the server must report before it counts as ready). None are built in. hearthd supervises each exactly as `hearth run` would, with the [supervise] values. A program without a path is looked up in hearthd's PATH, which under a login service is the PATH `hearth service install` was run with; an absolute path avoids the question. Optional per server: env, a table of variables set for it on top of hearthd's own (GGML_METAL_*, CUDA_VISIBLE_DEVICES, HF_HOME), and dir, the absolute working directory it starts in. And optionally model, ctx and cache_type together (the model as `hearth fit` takes it: a path, org/repo or an Ollama name): hearthd then checks before every start that the model at that context fits the device at all, and refuses to start one that never can, instead of letting it run out of accelerator memory. |

## `[state]`

| Key | Default | Meaning |
|---|---|---|
| `state.history_limit` | `50` | How many entries `log`, `follow` and `diff` show when no --limit is given, the latest first; they say when there is more. A whole history runs to thousands of snapshots, and an agent's context to far less. `log --full` (an archive) is not limited. |
| `state.max_note_bytes` | `4096` | Longest note `hearth note` records, in bytes: a note is a sentence or two about what was done, not a log. |
| `state.max_snapshots_per_kind` | `1000` | Snapshots kept per kind (ports, doctor, run, note) in the state directory: $HEARTH_STATE, or $XDG_STATE_HOME/hearth (default ~/.local/state/hearth). A hard cap: past it the oldest are deleted, whatever the tiers say. `hearth log` lists them, `hearth diff` compares two. Tagged snapshots are kept and not counted. A doctor snapshot is some tens of KB. |
| `state.max_tags` | `100` | Most tags at once. Tagged snapshots are kept past retention, so without a bound an agent naming moments in a loop would grow the history forever. Moving an existing name is always allowed. |
| `state.thinned_kinds` | `["ports", "doctor"]` | Kinds that are states of the machine (ports, doctor), thinned with age by the tiers below. Events (run, note) are only capped: every one matters. |
| `state.tiers` | `[{ every_ms = 0, within_ms = 3600000 }, { every_ms = 600000, within_ms = 86400000 }, { every_ms = 3600000, within_ms = 604800000 }]` | How thinned kinds age: within each window from now, one snapshot is kept per interval (every one when every_ms is 0); past the last window they are deleted. Defaults: every snapshot for an hour, one per 10 minutes for a day, one per hour for a week, so `hearth diff --from @1d` has a yesterday to compare with. |

## `[supervise]`

| Key | Default | Meaning |
|---|---|---|
| `supervise.admit_by_footprint` | `true` | hearthd holds a server's start while available memory is below what that server held when it last became ready, plus admit_headroom_bytes. That footprint is a lower bound (it may leave out memory-mapped weights, see ADR-000), so a held start is one that certainly would not fit. A server never measured starts; memory that cannot be read holds the start. |
| `supervise.admit_headroom_bytes` | `1073741824` | Kept free above that footprint. One GiB covers most of the short-term swing in available memory on a busy machine (ADR-000 measured a 3-sigma of 2.45 GiB over 90 s); the start goes ahead at the first poll it fits. |
| `supervise.backoff_factor` | `2` | Wait before a restart: starts here, grows by backoff_factor per exit up to the maximum, and resets once a server has stayed ready a whole window. The maximum may not exceed restart_window_ms, or exits would never share a window and a crash loop would go unnoticed. |
| `supervise.backoff_max_ms` | `8000` | Wait before a restart: starts here, grows by backoff_factor per exit up to the maximum, and resets once a server has stayed ready a whole window. The maximum may not exceed restart_window_ms, or exits would never share a window and a crash loop would go unnoticed. |
| `supervise.backoff_start_ms` | `500` | Wait before a restart: starts here, grows by backoff_factor per exit up to the maximum, and resets once a server has stayed ready a whole window. The maximum may not exceed restart_window_ms, or exits would never share a window and a crash loop would go unnoticed. |
| `supervise.output_line_bytes` | `1024` | Longest line of server output kept; the rest is cut. Servers that print progress bars without newlines would otherwise make one line of anything. |
| `supervise.output_lines` | `200` | Lines of each server's own output hearthd keeps, for `hearth logs NAME` and the MCP tool `logs`: enough to see why it failed, not a log archive. |
| `supervise.probe_interval_ms` | `1000` | How often the server is probed, and how many probes in a row may find it not serving (no answer, refused, or not the expected model) before it is called wedged and restarted. |
| `supervise.ready_timeout_ms` | `180000` | How long a started server has to answer as a runtime serving the expected model. Large models on a cold disk take minutes to load. |
| `supervise.restart_budget` | `5` | Exits tolerated before hearth gives up, counted since the server last stayed ready a whole restart_window_ms: more is a crash loop, and restarting a model that cannot load only burns the machine. A run that never stays ready that long counts, however long it took to fail. |
| `supervise.restart_window_ms` | `60000` | Exits tolerated before hearth gives up, counted since the server last stayed ready a whole restart_window_ms: more is a crash loop, and restarting a model that cannot load only burns the machine. A run that never stays ready that long counts, however long it took to fail. |
| `supervise.serialize_loads` | `true` | hearthd starts one server at a time: a server about to start waits while another it keeps is still loading (not yet ready), so two models never fill memory at the same moment, the commonest way several local models take a machine down. Measured admission (ADR-000) is the way past this once its gate has run. |
| `supervise.stop_grace_ms` | `5000` | SIGTERM, then SIGKILL after this. A llama.cpp server whose Metal backend latched after an out-of-memory error does not exit on SIGTERM. |
| `supervise.unresponsive_probes` | `3` | How often the server is probed, and how many probes in a row may find it not serving (no answer, refused, or not the expected model) before it is called wedged and restarted. |

## `[watch]`

| Key | Default | Meaning |
|---|---|---|
| `watch.confirm_rounds` | `2` | Rounds in a row a projected limit, or a ports warning (a server slow or configured past the device), must show before it is reported, and must be gone before it is reported cleared. One rate measured over one interval wobbles; without this a count hovering near the horizon would open and clear on alternate rounds. Kernel memory pressure is reported at once. |
| `watch.doctor_interval_ms` | `10000` | `hearth watch` observes on these intervals. Every observation is recorded, and state.tiers decides how much of it is kept as it ages. |
| `watch.in_hearthd` | `true` | Whether hearthd runs these rounds too, alongside keeping its servers. When it does, `hearth watch` refuses to run beside it, so nothing is reported twice. |
| `watch.limit_horizon_ms` | `3600000` | A resource growing at the measured rate is reported when it would reach its limit (the kernel's, or the process's) within this long. Growth alone is not reported: descriptor and thread counts move all the time. |
| `watch.ports_interval_ms` | `60000` | `hearth watch` observes on these intervals. Every observation is recorded, and state.tiers decides how much of it is kept as it ages. |
